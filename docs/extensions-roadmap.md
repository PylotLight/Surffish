# Extension support roadmap

There is no extension manager in the current build. The most sensible route is to build the extension and permission plumbing first, then decide which extensions are truly compatible instead of promising full Chrome-store support.

- **Create a small extension host:** load extensions into Sockfish's existing persistent browser session at startup, add enable/disable and removal controls, and give each extension a visible toolbar action or popup. Electron supports loading unpacked extensions per persistent session, but explicitly says arbitrary Chrome Web Store compatibility is not a goal and only a subset of extension APIs is supported ([Electron extension support](https://www.electronjs.org/docs/latest/api/extensions), [session API](https://www.electronjs.org/docs/latest/api/session)).
- **Show permissions before install/enable:** explain host access and permissions such as request interception, content scripts, and storage; keep an installed-extension list and make revocation easy. Treat an extension as code with access to pages, not as a harmless theme.
- **Built-in network ad blocking is prototyped:** Sockfish uses Ghostery's maintained ads-only filter set through the browser session, with cosmetic filtering disabled and list updates routed through the configured proxy. Clear update status and per-site controls remain future work. This avoids depending on extension APIs that may be missing and keeps filtering scoped to Sockfish's proxied session.
- **Then test real uBlock builds as an optional compatibility experiment:** load a trusted unpacked build and check background execution, request blocking, cosmetic filters, filter-list updates, and persistence against Sockfish's exact Electron/Chromium version. Do not assume that full uBlock Origin or uBlock Origin Lite will work just because Electron can load an unpacked extension; API compatibility is partial, and blocker features differ across browsers ([uBlock Origin's browser capability notes](https://github.com/gorhill/uBlock/wiki/uBlock-Origin-works-best-on-Firefox)).
- **For password managers, test their official extensions before building a vault:** try their supported Electron/Chromium packages, then implement the missing browser pieces they need—extension popups, reliable active-page identity, content-script messaging, and a secure autofill surface. Sockfish now has a per-tab model, but still needs extension popups and the associated permission, messaging, and autofill work.
- **Keep credentials out of Sockfish at first:** let the password manager's own extension/app manage its encrypted vault; ask for narrowly scoped site permissions and avoid logging field values or exposing them to the React shell. Only consider a native credential store if a concrete manager cannot work through its supported extension.
- **Gate release on a compatibility and security suite:** verify that extensions cannot access local files or the app's preload bridge, that granted host permissions are enforced, that extension traffic follows the configured proxy, and that updates/removal take effect after restart.

## Engine choices

Sockfish already renders pages with Chromium/Blink through Electron's `WebContentsView`. The gap is the browser-extension host, not the page-rendering engine: Electron explicitly limits extension support to a subset of APIs and unpacked extensions ([Electron compatibility list](https://www.electronjs.org/docs/latest/api/extensions)).

- **Stay on Electron:** the least disruptive route. Add an extension manager and permissions UI, then qualify a short list of target extensions against this Electron version. The supported API surface includes selected `runtime`, `scripting`, `storage.local`, `tabs`, and `webRequest` APIs, not the full Chrome extension platform.
- **Move to CEF or Qt WebEngine:** both keep a Chromium/Blink rendering base but replace Electron's embedding/runtime integration. CEF is a C/C++ embedding framework ([CEF overview](https://cef-builds.spotifycdn.com/docs/stable.html)); Qt WebEngine also exposes Chromium-backed page rendering ([Qt feature overview](https://doc.qt.io/qt-6/qtwebengine-features.html)). Neither should be assumed to provide Chrome-browser extension parity; each requires a compatibility prototype and a substantial shell/packaging migration.
- **Use a full Chromium-based browser platform:** this is the direction if broad Chrome extension compatibility is a hard requirement. It means adopting or building the browser-level extension host, update and permission systems, UI surfaces, and ongoing Chromium security updates—not swapping a rendering library into this Electron app. Using installed Chrome externally is cheaper but would no longer embed those pages in Sockfish.
- **Use Gecko:** a different engine means a deeper rewrite. Mozilla's maintained GeckoView embedding path is aimed at Android applications ([GeckoView overview](https://mozilla.github.io/geckoview/)), so it is not a drop-in desktop replacement for this Electron shell.

Recommendation for the current prototype: keep Electron, measure the exact extensions that matter, and only revisit the runtime if those tests fail for a core use case.
