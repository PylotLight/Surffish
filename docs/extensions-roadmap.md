# Extension support roadmap

There is **no general extension manager** in the current build. Electron can load extensions into a persistent session, but supports only a subset of Chrome extension APIs and does not target general Chrome Web Store compatibility. Bramble has its own first-party integration: install/update/version/permissions live in Sockfish Settings, while its compact popup is the sole extension-style toolbar action and vault setup remains in Bramble’s UI. This does not make Electron a general Chrome/Firefox extension host. General installed-extension controls, enable/disable/removal, per-extension popup hosting, and permission lifecycle/revocation remain future work.

## Password-manager compatibility

The latest tested official [Bitwarden Chrome release](https://github.com/bitwarden/clients/releases/tag/browser-v2026.9.3) is Manifest V3, with a service worker and `action` popup; it is not the old MV2 shape. An inert MV2 compatibility fixture remains useful, but it does not describe today's official package. The Electron 44.7.0 / Chromium 152 probe accepted the generic MV2 fixture, injected a content script, completed `chrome.runtime` messaging and a `storage.local` round-trip, and loaded its popup document. A Bitwarden-shaped MV2 fixture exposed and successfully used `chrome.alarms` and `chrome.webRequest`, but `contextMenus`, `webNavigation`, `notifications`, and `commands` were absent. The official MV3 release results are recorded below. `webRequest` may conflict with Sockfish's adblocker because Electron gives conflicting session `webRequest` handlers precedence.

The current [Bramble Chromium manifest](https://github.com/flythenimbus/bramble/blob/main/packages/manifests/chromium/manifest.json) is Manifest V3 and requests APIs such as alarms, idle, offscreen documents, identity, and web-authentication proxy. Sockfish's exact runtime probe loaded an MV3 worker and completed its content-script/background message round-trip. Actual `storage.local` and `storage.session` round-trips, alarm create/get, idle query, and offscreen create/close all succeeded. `storage.onChanged` exists and delivered to the content script, but the same event was not observed in the service worker during its own storage round-trip. Electron lacks the Chromium build's `identity` and `webAuthenticationProxy` APIs; these remain unavailable. Bramble also asks for `<all_urls>` host access, which any integration must explain clearly.

A static compatibility checker is available for unpacked builds: `npm run check:password-extension -- bitwarden <unpacked-dir>` (use `bramble` for Bramble). It reads `manifest.json` and scans JavaScript text for likely `chrome.*` / `browser.*` API references without executing code. It reports permission, namespace, service-worker, popup/commands, Firefox-manifest, host-access, and `webRequest`/ad-blocker risks. Extract `.xpi` packages before inspecting; the checker never loads an extension. A clean static report still does not prove runtime compatibility. Keep credentials inside each manager's encrypted vault; Sockfish must not log field values or expose them to the React shell.

`npm run test:electron-extensions` launches the exact installed Electron/Chromium runtime in isolated processes against inert local fixtures: a generic MV2 baseline, a Bitwarden-shaped MV2 permission profile, a Bramble-like Chromium MV3 service-worker profile with real storage/alarm/idle/offscreen operations, and a Firefox-shaped MV3 profile using `browser.*`, `background.scripts`, Gecko metadata, and separate MAIN/isolated content scripts. The generic MV2 fixture is asserted end-to-end; other outcomes are reported separately and do not imply real-manager compatibility. Electron accepted the Firefox-shaped package but warned that MV3 `background.scripts` and `browser_action` require MV2; its isolated content script had the browser alias but no background reply, its popup did not load, and the MAIN-world page hook ran without extension APIs. CI runs this on Linux under Xvfb. `npm run test:electron-host-bridge` separately checks the opt-in frame-mapping prototype against Sockfish's actual `BrowserTab`/`WebContentsView` and synthetic loopback pages; it is also run in Linux CI. Native `WKWebExtensionController` acceptance/runtime checks remain separate and run on macOS CI.

## Bramble Firefox-build integration

Sockfish offers a Settings-based install/update flow for the latest stable Bramble Firefox GitHub release, which publishes a ready-to-load ZIP and `SHA256SUMS`; users do not need to build Bramble or install its source toolchain. The installer checks GitHub release asset digests, the published checksum, and archive safety; it previews the version and requested permissions before explicit activation. The adapter stages a private copy, converts the known Firefox module background entry to Electron’s MV3 service-worker shape, removes the unsupported `identity` permission, and provides `browser` aliases only in Bramble-owned contexts. Sockfish hosts the actual Bramble popup/options UI and a hidden same-session `offscreen.html` window for vault crypto. This remains Bramble-specific and does not add a general extension manager.

**Verified locally:** Bramble’s real UI creates a disposable vault; it can be force-locked and unlocked again. With Bramble’s opt-in **Use Bramble for passkeys** preference enabled in the isolated test profile, the Firefox MAIN-world bridge handles a localhost RP’s consented ES256 passkey registration and subsequent assertion inside Sockfish. The test verifies the assertion signature against the registration public key, RP ID hash, origin, challenge, user-presence, and user-verification flags. It uses a temporary profile, random runtime-only test values, localhost, and blocked external DNS; it logs/saves no vault password, recovery code, or passkey private key. Run `npm run test:bramble-app-poc -- /path/to/bramble/packages/platform-extension/dist-firefox` after `npm run build`; see [the integration and updater notes](bramble-integration.md).

This verifies the dedicated Bramble Firefox-build integration only; it does not prove the Chromium extension API path or arbitrary Firefox add-on compatibility. Bramble’s optional Google Drive/OAuth backup is unsupported because `identity` is removed. Do not infer general password autofill or general extension compatibility from this specific integration.

## Official Bitwarden build probe (Chrome 2026.9.3)

The official release artifact is `browser-v2026.9.3` / `dist-chrome-2026.9.3.zip` (release SHA-256 `7185bad74d44b1d7e81b3dc9858a206bf9debff272d7e5bfc7f56a4b9d942ca0`). It declares MV3 `background.service_worker=background.js`, `action.default_popup=popup/index.html`, content scripts, broad HTTP(S) host access, and **no manifest options page**. The probe used a fresh temporary profile; it did not log in, import a vault, or use credentials, and its session cancelled non-loopback network requests. Bitwarden's expected `https://api.bitwarden.com/config` requests were blocked by design.

**Stock Electron result (unmodified release):** Electron accepted the unpacked package and emitted `extension-ready`, but the service worker failed registration (status 15) at missing `chrome.webNavigation.onCommitted`. The real popup document loaded, but Bitwarden's popup bootstrap errored because `chrome.tabs.getCurrent` is not a function; its root remained empty. These failures block an out-of-the-box integration; a successfully loaded extension document is not evidence of working autofill.

**Isolated host experiment (not product support):** a disposable copy used a temporary manifest wrapper around Bitwarden's original worker bundle, listener-registration-only `webNavigation` event objects (no fabricated navigation events), and an experimental IPC relay for `getAllFrames` backed by Sockfish's real registry and `WebFrameMain` tree. After the listener-only wrapper let the original worker continue, it also reported missing `chrome.permissions.contains` and unsupported notification-click handling; its server-config request was blocked by policy. The popup check used CDP `Page.addScriptToEvaluateOnNewDocument` for a test-only `tabs.getCurrent` implementation; the official popup HTML and original build files were not modified. The original background bundle responded to the probe, the actual action popup rendered its unauthenticated onboarding/log-in surface, and three Bitwarden isolated content-script worlds appeared on the synthetic top-level/nested-frame page. Chromium tab ID equalled the page `WebContents.id`; the main-frame extension ID was `0`, child IDs matched `frameTreeNodeId`, and bridged frame/parent results exactly matched the live frame tree. This validates a **small host-side mapping prototype only**; the worker's navigation listeners were not fired and the temporary shims do not provide extension API support in Sockfish.

To reproduce the fixture, run `npm run test:electron-host-bridge` (under Xvfb on headless Linux). For a real unpacked build, first run the unmodified diagnostic with `npm run probe:electron-extension-real -- /path/to/unpacked`; then, if needed, run the host experiment with `SOCKFISH_PROBE_EXTENSION_DIR=/path/to/unpacked npm run test:electron-host-bridge`. The latter wraps a temporary copy and labels every experimental override in its JSON report. Neither command authenticates or uses vault data.

**Remaining password and general-extension gaps:** normal password selection/fill was not exercised against a real signed-in manager account. The stock MV3 worker still lacks required `webNavigation` and `permissions` methods, and Sockfish still lacks a general extension manager, toolbar-popup host, permission lifecycle, and full navigation-event bridge. Bramble’s tested passkey flow is limited to its dedicated Firefox-build integration above; it does not change the Bitwarden result or establish general extension compatibility.

## Other compatibility checks

Ad blocking runs uBO's own lists (network, cosmetic and scriptlet filters, early injection via a frame preload) on Ghostery's matcher; list updates use the configured proxy and per-site switches apply to all three. Real uBlock builds are a separate compatibility experiment: verify background execution, request blocking, cosmetic filters, list updates, and persistence against Sockfish's exact Electron/Chromium version. Do not assume that full uBlock Origin or uBlock Origin Lite works just because Electron can load an unpacked extension ([uBlock Origin's browser capability notes](https://github.com/gorhill/uBlock/wiki/uBlock-Origin-works-best-on-Firefox)).

## Engine choices

Sockfish already renders pages with Chromium/Blink through Electron's `WebContentsView`; the gap is the browser-extension host, not the rendering engine.

- **Stay on Electron:** the least disruptive route. Electron documents selected `runtime`, `scripting`, `storage.local`, `tabs`, and `webRequest` APIs, not the full Chrome extension platform.
- **Move to CEF or Qt WebEngine:** both retain Chromium/Blink but replace much of the Electron shell; neither should be assumed to provide Chrome-browser extension parity. CEF is a C/C++ embedding framework ([overview](https://cef-builds.spotifycdn.com/docs/stable.html)); Qt WebEngine exposes Chromium-backed rendering ([features](https://doc.qt.io/qt-6/qtwebengine-features.html)).
- **Use a full Chromium-based browser platform:** this is the direction if broad Chrome extension compatibility is a hard requirement. It entails an extension host, update and permission systems, UI, and ongoing Chromium security updates; it is not an engine toggle.
- **Use Gecko:** a deeper rewrite. Mozilla's maintained GeckoView embedder is aimed at Android, not a drop-in desktop Electron replacement ([GeckoView overview](https://mozilla.github.io/geckoview/)).
- **Prototype native WebKit on macOS:** Apple's `WKWebExtensionController` is available from macOS 15.4 and can host Safari-style extensions in a `WKWebView`; SOCKSv5 data-store proxy configuration is available from macOS 14. This requires a separate native browser-view/profile implementation, not a replacement Electron setting. [See the WebKit evaluation and extension candidates](native-webkit-evaluation.md).

For the current prototype, keep Electron, measure the exact extensions that matter, and revisit the runtime only if those tests fail for a core use case.

## Passkey support in Electron

Sockfish's app-level WebAuthn and Bramble's passkey provider are separate paths. Sockfish's Electron dependency range begins at 44.5.1; the POC probes ran on Electron 44.7.0 / Chromium 152. Electron exposes [`app.configureWebAuthn`](https://www.electronjs.org/docs/latest/api/app#appconfigurewebauthnoptions-macos) on macOS; its `touchID` option enables the platform authenticator but requires a matching `keychain-access-groups` signing entitlement and stores device-bound credentials.

Sockfish does not configure or sign for that native macOS path. The verified Bramble integration instead loads Bramble’s Firefox build and uses its MAIN-world bridge as the opt-in authenticator for websites inside Sockfish. See [Bramble Firefox-build integration](bramble-integration.md); it is intentionally not presented as native Electron WebAuthn or general passkey support.
