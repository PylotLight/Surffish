# Extension support roadmap

There is no extension manager in the current build. Electron can load unpacked extensions into a persistent session, but supports only a subset of Chrome extension APIs and does not target general Chrome Web Store compatibility ([extension support](https://www.electronjs.org/docs/latest/api/extensions), [session API](https://www.electronjs.org/docs/latest/api/session)). The first host needs an installed-extension list, enable/disable and removal controls, and a toolbar popup for each extension. Installation should show the extension's host access and permissions before its code is allowed to run, with easy revocation afterward.

## Password-manager compatibility

The current [Bitwarden manifest](https://github.com/bitwarden/clients/blob/main/apps/browser/src/manifest.json) is Manifest V2, but declares APIs and UI hooks outside Electron's documented subset, including context menus, web navigation, notifications, commands, and a browser-action popup. The Electron 44.5.1 / Chromium 152 probe accepted an inert MV2 package, injected a content script, completed `chrome.runtime` messaging and `storage.local` round-trip, and rendered its popup document. A Bitwarden-shaped manifest with the declared permissions exposed and successfully used `chrome.alarms` and `chrome.webRequest`, but `contextMenus`, `webNavigation`, `notifications`, and `commands` were absent (Chromium also warned that the first three permissions are unknown or malformed). Chromium emits an MV2 deprecation warning. Its `webRequest` use may conflict with Sockfish's adblocker because Electron gives conflicting session `webRequest` handlers precedence.

The current [Bramble Chromium manifest](https://github.com/flythenimbus/bramble/blob/main/packages/manifests/chromium/manifest.json) is Manifest V3 and requires a background service worker plus APIs such as alarms, idle, offscreen documents, identity, and web-authentication proxy. Although Electron's docs do not list extension service workers, Sockfish's exact runtime probe loaded an MV3 worker and completed its content-script/background message round-trip. Actual `storage.local` and `storage.session` round-trips, alarm create/get, idle query, and offscreen create/close all succeeded. `storage.onChanged` exists and delivered to the content script, but the same event was not observed in the service worker during its own storage round-trip, so that background-context behavior remains a material risk. The loader warned that `identity` and `webAuthenticationProxy` permissions are unknown, and those two API objects were absent. Presence is not proof that every API method, lifecycle event, permission flow, or Bramble workflow works. Bramble also asks for `<all_urls>` host access, which means the eventual host must explain that broad access clearly. Its required WebAuthn-proxy API is the clearest passkey blocker.

A static compatibility checker is available for unpacked builds: `npm run check:password-extension -- bitwarden <unpacked-dir>` (use `bramble` for Bramble). It reads `manifest.json` and scans JavaScript text for likely `chrome.*` / `browser.*` API references without executing code. It reports permission, namespace, service-worker, popup/commands, Firefox-manifest, host-access, and `webRequest`/ad-blocker risks. Extract `.xpi` packages before inspecting; the checker never loads an extension. A clean static report still does not prove runtime compatibility. The first extension implementation should keep credentials inside each manager's own encrypted vault; Sockfish should not log field values or expose them to the React shell.

`npm run test:electron-extensions` launches the exact installed Electron/Chromium runtime in isolated processes against inert local fixtures: a generic MV2 baseline, a Bitwarden-shaped MV2 permission profile, a Bramble-like Chromium MV3 service-worker profile with real storage/alarm/idle/offscreen operations, and a Firefox-shaped MV3 profile using `browser.*`, `background.scripts`, Gecko metadata, and separate MAIN/isolated content scripts. The generic MV2 fixture is asserted end-to-end; other outcomes are reported separately and do not imply real-manager compatibility. Electron accepted the Firefox-shaped package but warned that MV3 `background.scripts` and `browser_action` require MV2; its isolated content script had the browser alias but no background reply, its popup did not load, and the MAIN-world page hook ran without extension APIs. CI runs this on Linux under Xvfb. Native `WKWebExtensionController` acceptance/runtime checks remain separate and run on macOS CI.

## Other compatibility checks

Network ad blocking is already prototyped with Ghostery's maintained ads-only filter set through the browser session; cosmetic filtering is disabled and list updates use the configured proxy. Clear update status and per-site controls remain future work. Real uBlock builds are a separate compatibility experiment: verify background execution, request blocking, cosmetic filters, list updates, and persistence against Sockfish's exact Electron/Chromium version. Do not assume that full uBlock Origin or uBlock Origin Lite works just because Electron can load an unpacked extension ([uBlock Origin's browser capability notes](https://github.com/gorhill/uBlock/wiki/uBlock-Origin-works-best-on-Firefox)).

## Engine choices

Sockfish already renders pages with Chromium/Blink through Electron's `WebContentsView`; the gap is the browser-extension host, not the rendering engine.

- **Stay on Electron:** the least disruptive route. Electron documents selected `runtime`, `scripting`, `storage.local`, `tabs`, and `webRequest` APIs, not the full Chrome extension platform.
- **Move to CEF or Qt WebEngine:** both retain Chromium/Blink but replace much of the Electron shell; neither should be assumed to provide Chrome-browser extension parity. CEF is a C/C++ embedding framework ([overview](https://cef-builds.spotifycdn.com/docs/stable.html)); Qt WebEngine exposes Chromium-backed rendering ([features](https://doc.qt.io/qt-6/qtwebengine-features.html)).
- **Use a full Chromium-based browser platform:** this is the direction if broad Chrome extension compatibility is a hard requirement. It entails an extension host, update and permission systems, UI, and ongoing Chromium security updates; it is not an engine toggle.
- **Use Gecko:** a deeper rewrite. Mozilla's maintained GeckoView embedder is aimed at Android, not a drop-in desktop Electron replacement ([GeckoView overview](https://mozilla.github.io/geckoview/)).
- **Prototype native WebKit on macOS:** Apple's `WKWebExtensionController` is available from macOS 15.4 and can host Safari-style extensions in a `WKWebView`; SOCKSv5 data-store proxy configuration is available from macOS 14. This requires a separate native browser-view/profile implementation, not a replacement Electron setting. [See the WebKit evaluation and extension candidates](native-webkit-evaluation.md).

For the current prototype, keep Electron, measure the exact extensions that matter, and revisit the runtime only if those tests fail for a core use case.

## Passkey support in Electron

Sockfish currently depends on Electron 44.5.1, which exposes [`app.configureWebAuthn`](https://www.electronjs.org/docs/latest/api/app#appconfigurewebauthnoptions-macos) on macOS. Its `touchID` option enables the platform authenticator for web pages using `navigator.credentials.create()` and `navigator.credentials.get()`. Electron requires a matching `keychain-access-groups` code-signing entitlement; credentials are stored in the Mac's Secure Enclave and are device-bound rather than synced through iCloud Keychain.

This is **app-level WebAuthn support**, not evidence that a password-manager extension can provide passkeys in Sockfish. It does not implement the extension APIs, popup UI, or host integration that Bitwarden or Bramble might need. Sockfish does not currently call `configureWebAuthn` or have the required macOS signing entitlement configured, so passkeys are not enabled or tested in this app. This could be a separate macOS browser feature, but it would not resolve extension compatibility on its own.
